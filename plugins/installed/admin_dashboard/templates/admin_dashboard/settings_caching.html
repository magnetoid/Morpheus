Storefront caching

Tune what Django emits to Cache-Control headers — Cloudflare honours these for its edge cache, browsers honour them for local cache. Per-product/category invalidation still happens via the hooks layer.

In-app cache for rendered HTML responses. 0 = off. 300 = 5 min (recommended baseline for non-logged-in customers).

Cache-Control max-age emitted for /static/ and /media/. 31536000 = 1 year (standard, paired with hashed filenames).

Sent on storefront HTML responses. CF interprets s-maxage for its edge; browsers honour max-age. Recommended: public, max-age=0, s-maxage=300, must-revalidate.

{# ───── Headless storefront note ──────────────────────────────────── #}

Works with a headless storefront?

Yes. The three layers operate independently:

  • Cloudflare edge sits in front of HTTP regardless of what serves the response — Django, Next.js, Nuxt, anything. It caches the response by URL + Vary headers. The Cache-Control headers above (s-maxage) drive it.
  • Application cache (Redis) is used by GraphQL resolvers, ORM, computed prices — the headless frontend benefits because every query Linda or the headless storefront sends through /graphql/ hits this cache first.
  • Storefront page cache only applies to Django-rendered HTML pages (the dot_books theme). In a headless setup these views aren't served; the setting is harmless if unused.

One thing to add for a real headless stack: emit explicit Cache-Control: public, s-maxage=N headers on your GraphQL responses (Strawberry hook) so CF caches identical queries at the edge. Currently GraphQL responses are uncached by default. Want me to wire that?
