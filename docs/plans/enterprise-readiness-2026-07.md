# Morpheus OS — Enterprise-Readiness Audit

> Generated 2026-07-02 by a 14-dimension fan-out audit (66 agents, adversarially verified).

> Method: each dimension audited by an Explore agent grounding findings in `file:line` evidence; every
> critical/high finding re-checked by an independent skeptic against the actual code; refuted findings dropped.


## Overall maturity: **6/10**


Morpheus is an ambitious, architecturally coherent commerce platform with genuinely strong bones — a clean hook-based plugin kernel with CI-ratcheted core-boundary enforcement, disable-test gating, enterprise-grade circuit breakers, payment idempotency, passwordless OTP + staff MFA, and a transactional-outbox event model. But it is NOT enterprise-production-ready, and the gap is concentrated exactly where it hurts most given that every push to main auto-deploys dotbooks.store with no staging, no manual approval gate, no post-deploy smoke test, no canary/blue-green, and no automated DB-migration rollback. Two production-safety defects are effectively latent outages waiting to happen: the transactional-outbox publisher (process_outbox) is implemented but never registered on the Celery beat schedule, so events silently accumulate undelivered and the at-least-once guarantee is broken today; and the CVE audit gate is continue-on-error while all dependencies float on >= ranges with an empty lock file and no container image scan. Layered on top are real correctness/compliance risks — plaintext SMTP credentials and customer PII at rest (GDPR Art. 32), partial-failure GDPR anonymization that still marks the account deleted, unclassified payment-refund exceptions that strand refunds, and webhook double-delivery with no idempotency key. The test suite looks large (~1500-2100 functions) but 22+ shipped plugins have pytest-style tests that Django's test runner silently never executes in CI, coverage is floored at a permissive 40%, and mypy is installed but never run. This is a 'strong architecture, weak operational hardening' system: the design would earn a 7-8, but the unmitigated prod-deploy blast radius and the confirmed data-loss/compliance defects pull the honest enterprise-readiness score to a 6. It is shippable for a single-operator store today; it is not yet safe for enterprise/multi-tenant SLAs without Phase 1 remediation.

## Top confirmed risks (ordered)

1. process_outbox is never registered on the Celery beat schedule (morph/celery.py:35-48 has only core-errors-prune + core-check-for-updates), so OutboxEvent rows accumulate undelivered and the platform's advertised at-least-once event guarantee is broken RIGHT NOW — every NATS subscriber (inventory commits, downstream integrations) silently misses events until someone triggers the task manually. CRITICAL, prod-safety, immediately exploitable.

2. Every push to main auto-deploys production (dotbooks.store) with NO staging, NO manual approval gate, NO post-deploy smoke test, NO canary/blue-green, and NO automated DB-migration rollback (cd.yml is 29 lines, build-and-push only; core/updates.py reverts code but leaves schema in post-crash state requiring manual pg_restore). Two documented 503 outages (PR #62, #64) already happened this way. Any boot error or bad migration is a live outage until hot-fixed.

3. PII stored unencrypted at rest: smtp_password is a plaintext CharField (core/models.py:49) and order email/ip_address/user_agent are plaintext (orders/models.py) — a DB dump leaks SMTP credentials and all customer contact/identity data. GDPR Art. 32 violation. Plugin API keys (Amazon/Google/Meta) are also plaintext in PluginConfig.config JSONField with no audit trail.

4. Payment refund exceptions are swallowed with a bare except Exception (stripe_gateway.py:60-62) that returns a generic error dict with no transient-vs-permanent classification — transient network failures are treated as permanent, so refunds silently strand with no retry, damaging merchant/customer trust. Compounded by unprotected Stripe vault operations (create_setup_intent, list_payment_methods) that burn a full 20s timeout on every call during a Stripe outage with no circuit breaker.

5. Task idempotency is not enforced: deliver_webhook (webhooks_ui/tasks.py) unconditionally re-POSTs on redelivery and OutboxEvent has no msg_id/idempotency key for NATS dedup — broker redelivery or manual retry causes duplicate webhook delivery (duplicate downstream charges, double emails, repeated side effects) with no server-side guard.

6. 22+ shipped plugins (checkout_experience, subscriptions_plus, returns_portal, one_click, referrals, customers, marketing, tracking, etc.) have tests that CI never runs: they are pytest-style module-level functions in tests/__init__.py, but CI uses Django's unittest runner which reports 'Ran 0 tests' for them. Business-critical flows (checkout, subscriptions, returns — including the returns_portal parallel-model regression CLAUDE.md explicitly warns about) have zero runtime validation despite tests existing in the repo.

7. Supply-chain controls are effectively off: the pip-audit CVE gate is continue-on-error (ci.yml:51), all 53 dependencies float on >= ranges with an empty uv.lock, there is no container image CVE scan / SBOM / cosign signing in cd.yml, and no scheduled CVE rescans — a known-vulnerable transitive dep ships straight to prod on the next main push with nothing blocking it.

8. 430+ undeclared cross-plugin model imports bypass the hook bus (e.g. advanced_ecommerce/ai_assistant/agent_core import inventory.models without declaring it in requires), and storefront account sub-pages hard-query orders/customers models directly — both violate the delete/disable litmus tests (ADR 0013/0017): deleting a dependency plugin leaves dangling ModuleNotFoundError imports in siblings, and disabling orders/customers leaves broken /account/ URLs alive instead of vanishing.

## Phased roadmap


### Phase 1 — Stop the bleeding — restore event delivery, close the prod-deploy blast radius, and lock the supply chain

*Every item here is a confirmed CRITICAL/HIGH that is currently unmitigated AND amplified by auto-deploy-to-prod-with-no-staging. Broken event delivery (process_outbox), a wide-open deploy pipeline, and non-blocking CVE gates are the three fastest routes to a silent data-integrity failure or live outage; these must land before any structural work.*

- Register process_outbox on the beat schedule AND add max_retries/exponential backoff + a msg_id/idempotency key so transient NATS failures retry instead of permanently marking events FAILED (core/tasks.py, morph/celery.py)
- Add a post-deploy smoke-test gate + `needs: [ci]` dependency to cd.yml; make manage.py check --deploy blocking (--fail-level ERROR, drop `|| true`)
- Introduce a manual-approval / deployment-freeze gate for main→prod OR a staging branch Coolify watches separately, so no CI-passing commit auto-ships without a human checkpoint
- Flip pip-audit to enforcing (continue-on-error: false) after triage; add a container image CVE scan (trivy) + cosign signing to cd.yml
- Enforce webhook + outbox idempotency (idempotency_key column, pre-check on redelivery) to eliminate double-delivery / double-charge
- Fix asyncio.run() RuntimeError crash in process_outbox; classify payment-refund exceptions (StripeError transient vs permanent) so refunds retry instead of stranding
- Document an incident-response / migration-rollback runbook (expand OPERATIONS_RUNBOOK.md from 36 lines) and an automated backup-restore path in core/updates.py

### Phase 2 — Data integrity, compliance, and reliability hardening

*These are confirmed HIGH data-loss/compliance and reliability defects that are serious but not instantaneous outages. They require more than a config toggle (schema changes, encryption migrations, test authoring) so they follow the stop-the-bleeding phase, but they close the GDPR/financial-correctness exposure and give operators the observability to catch the next incident before customers do.*

- Encrypt PII at rest: SMTP credentials (core/models.py:49) and order email/ip/user_agent via field-level encryption; encrypt plugin API keys in PluginConfig.config and add a config-change audit trail
- Fix partial-failure GDPR anonymization (customers/services.py) so a failed deletion step aborts the whole operation rather than marking the account anonymised with PII remaining
- Wrap Stripe vault operations in a STRIPE_BREAKER circuit breaker; make cart-reservation failures fail-fast (raise) instead of silently degrading and masking stock races
- Add real DB-level CHECK constraints for business invariants (quantity>0, total>=0) and wrap multi-model checkout writes (Cart→Order→OrderEvent→Payment) in single atomic transactions
- Make the 22+ silently-unrun plugin test suites actually execute in CI (Django TestCase conversion or add pytest); add contract tests for checkout_experience, subscriptions_plus, returns_portal, refund error-cases
- Propagate request_id/trace_id across the NATS boundary and into Celery task kwargs so async failures correlate back to the originating request; add Prometheus/RED metrics + a /metrics endpoint

### Phase 3 — Structural modularity, coverage discipline, and API/operator maturity

*This is the long-horizon architectural debt that limits scale, agility, and true plugin swap-ability but does not threaten prod today. Done last because it is XL-effort, benefits from the tests and gates added in Phases 1-2 to refactor safely, and delivers the modularity/API-discoverability polish that separates a capable platform from a FAANG-grade one.*

- Add a plugin-to-plugin import gate (parallel to check_core_boundary.py) and migrate the 430+ undeclared cross-plugin model imports to hooks/contribution APIs; declare optional_requires
- Migrate storefront account sub-pages (orders/returns/addresses/downloads) to a contributed ACCOUNT_PAGES hook so they vanish on disable (satisfy ADR 0013 litmus); add a CI plugin-deletion test for high-dependency plugins
- Raise coverage floor to 60% with per-package minimums (core 85%, payments/orders/catalog 80%), wire mypy from non-blocking baseline to enforcing, and add per-view permission-boundary test matrix
- Publish OpenAPI 3.1 for /v1/* and a schema endpoint for GraphQL; add MCP requires_approval enforcement + approval UI + audit trail, and standardized rate-limit headers across REST/GraphQL/MCP
- Adopt a real lockfile (uv pip compile / populate uv.lock), add SBOM generation and scheduled weekly CVE rescans; add secret-rotation tooling and a runtime feature-flag system
- Extract SEO/localization/digital fields off the 696-LOC catalog Product god-object into OneToOne plugin extensions; pay down the 2 remaining core→plugin boundary violations and the core/assistant/tools direct-import debt

### Security & Authorization — maturity 7/10

Morpheus OS has strong fundamentals: passwordless email-OTP auth with rate limiting, API key hashing, RBAC via role bindings, GraphQL permission helpers, CSP enforcement on admin surfaces, and comprehensive safety boundaries for AI code changes. CSP remains report-only on the storefront pending violation data, delaying enforcement.

### Config & Secrets Management — maturity 7/10

Morpheus implements solid 12-factor practices with python-decouple env var management, comprehensive SECRET_KEY/ALLOWED_HOSTS validation for production, and write-only password field masking in the plugin config UI. However, it lacks formal secret rotation, there is no separate staging environment (production is the only real target), and bare Exception blocks silently mask env var parsing failures in critical config paths.


**Strengths:** 12-factor compliance: All secrets sourced from environment via decouple.config(), never hardcoded; Production safety gates: Explicit validation errors when DEBUG=False and SECRET_KEY/ALLOWED_HOSTS/CORS_ALLOWED_ORIGINS are unset; Write-only password fields: JSON-schema format:password fields render masked, never echo stored secrets back (test coverage in place); Sentry secret scrubbing: Automatic redaction of password/token/card/secret keys and auth headers before sending to error tracking; Plugin-level config isolation: Each plugin stores own config in PluginConfig.config JSONField with secrets marked via schema format; Multi-environment draft support: Environments plugin provides dev/staging/production with settings_overrides and snapshot/promotion flow; Database read-replica routing: PrimaryReplicaRouter handles read/write separation transparently; OpenTelemetry PII scrubbing: Automatic redaction of emails/phone/IPv4 in traces before export


**Confirmed findings:**

- **[HIGH]** Silent exception handling suppresses config initialization errors — `core/email.py:32-33, core/observability.py:77-78, core/sentry.py:104-105` (effort M)
  - Gap: Bare except Exception: pass blocks silently swallow failures when reading StoreSettings from database or initializing observability/Sentry. If the database connection fails or OTEL SDK import fails, the app boots successfully with degraded functionality (no email logging, no tracing, no Sentry) and no logged warning to alert operators.
  - Fix: Replace bare except Exception blocks with specific exception handling. In core/email.py, catch DatabaseError and log a warning. In core/observability.py line 77-78, log the exception at WARNING level. In core/sentry.py line 104-105, the existing logger.error call is correct—match that pattern. 1. **core/email.py:32-33** (REAL, NOT LOGGED): The `except Exception: pass` block silently swallows all exceptions from `StoreSettings.objects.first()`. If the database is unavailable or the migration hasn't run, the exception is caught with zero logging. 2. **core/observability.py:77-78** (REAL, INSIDE SPAN PROCESSOR): The `except Exception: pass` in `_PIIScrubberProcessor.on_end()` is intentional—it prevents PII scrubbing errors from breaking spans. 3. **core/sentry.py:104-105** (CORRECTLY LOGGED, NOT A GAP): Line 104-105 catches exceptions but DOES log with `logger.error('sentry: init failed: %s', e, exc_info=True)`. This is NOT silent—it logs with full stack trace.

**The real vulnerability is in core/email.py:23-33**: If database connectivity fails or the StoreSettings table doesn't exist, the exception is silently caught (line 32: `except Exception: pass`), and the backend degrades to console output WITHOUT any warning to operators. No log entry warns operators that SMTP config initialization failed.

The settings.py wrapper around init_sentry (lines 774-779) DOES add a safety net, but the bare `except Exception: pass` in email.py (initialized at request time via `EMAIL_BACKEND`) has no such guard.

Severity: HIGH — Silent SMTP initialization failure could leave a production store unable to send transactional emails (password resets, order confirmations) without operator awareness.
- **[HIGH]** No secret rotation or expiration policy — `morph/settings.py lacks rotation configuration, plugins/models.py:config JSONField has no versioning` (effort L)
